# TelyinCore Infinity 插件开发规范 v1.13

版本：1.13 · 2026-11-03 · Python Infinity API 仍为 1。
本版替代 v1.12，纳入 r93 已发布约束及 r95 人工投递处置接口；随本次 r96 一并发布。旧章节中的候选/验收历史只说明当时状态，不代替当前版本核验。

“必须”表示开发和评审约束，不表示任意宿主和第三方插件都已实现对应能力。加载插件前仍需核对实际部署的接口。
本轮修复按用户决定结项：201项限定合同验收，8项能力边界/后续需求单列；不宣称209项无条件技术闭合。物理断电、同权限恶意写者和未登记原生任务全集不在当前保证范围。
规范版本与 Infinity API 版本独立；本次不改变插件清单中的 api=1，也不任意提升前端package版本。

示例、检查单与命令不是服务启停、真实外发或部署授权。

2026-11-04 文档补充：加入面向全部插件的可选配置页排版参考，不改变 Infinity API、插件版本或既有强制约束。

## 1. 范围与信任边界

Infinity 承载可选世界适配器、工具实现和外部服务连接；事件库、总线、主循环、人格与记忆属于核心。
本地插件与 GitHub 插件使用相同清单、生命周期和配置页。GitHub 是发现/分发来源，不是运行权限门槛。
Python 插件在 TelyinCore 进程内运行，不是安全沙箱：启用前须信任源码。
配置页 iframe 的隔离不代表 Python 插件也被隔离。

## 2. 目录与清单

```text
core/extensions/my-infinity-demo/
  package.json
  index.py
  config.example.json        # 可选，JSON 对象
  config.schema.json         # 可选，轻量字段声明
  config.html                # 可选，单文件配置页面
  README.md                  # 建议
```

本地使用可直接放置合规目录，不必上传 GitHub；之后刷新插件列表，手动启用。
不要复制私人 config.json、账号令牌、Bot 人设或运行日志给其他用户。

```json
{
  "name": "my-infinity-demo",
  "version": "0.1.0",
  "author": "你的名字",
  "main": "index.py",
  "description": "插件用途",
  "keywords": ["core-infinity"],
  "license": "MIT",
  "telyincore": {
    "kind": "infinity",
    "api": 1,
    "displayName": "演示插件",
    "configSchema": "config.schema.json",
    "configPage": "config.html"
  }
}
```

`author` 是清单中的作者字段，使用非空字符串，写实际作者或维护者名称，不得用匿名占位。
随 TelyinCore 提供、位于 `builtin/` 的官方内置插件，`author` 必须精确为 `Telyin`；
第三方插件保持其实际作者，不因包名以 `core-infinity-` 开头而被改写。
前端和宿主只读取清单中的 `author`，不要在页面、适配器或按包名前缀硬编码作者。

name 应稳定且唯一，并作为安装最终目录的一部分校验，不能只验证下载 URL 的文件名。
采用单路径段名称，拒绝 `@scope/name`、斜杠、反斜杠、冒号、控制字符、`.`、`..`、尾点、尾空格以及 Windows 设备名（包括带扩展名的设备名）。不靠截断、去点或替换字符“修复”不合规名称。
这与 npm scoped package 命名不同；不要把本地旧目录可加载当作安装器承诺兼容。
main、configSchema、configPage 必须指向插件目录内文件，禁止越界；实际解析路径、链接及最终发布目录也必须核对。安装强化已纳入本次 r39 部署版本；其他宿主仍须核对相应版本，不能由文档推断已具备该保护。
configSchema/configPage 可省略；schema 也可内联对象。api 当前为整数 1，不是任意版本区间。
插件版本建议使用语义化版本。依赖环境须在 README 列明，不应在 import/start 中静默 pip 安装。

### 2.1 列表简介、详情与来源显示

所有核心、第三方本地和 GitHub 插件的列表卡片简介统一最多显示两行，超出部分由 CSS 收起。
`description` 的存储、接口返回、检索与筛选必须保留完整字符串，不得按两行或字符数截断；
前端也不得用 JavaScript 截断字符串伪装两行。两行限制只作用于卡片显示层。
详情面板保留完整正文和原有换行，长单词允许在必要时断行，不沿用卡片的行数限制。
插件来源按真实清单标记显示：随 TelyinCore 提供的内置插件（无论当前是否安装）显示“核心”，
第三方本地或 GitHub 插件保留真实来源，不按包名前缀推断或改写。

插件清单写 `LicenseRef-TelyinCore-NonCommercial-1.0`，对应根目录
[《TelyinCore 非商业使用与受限分发许可》1.0](../LICENSE)。这是**源码可见的受限许可**，
不是 MIT、GPL 等 OSI 标准开源许可，也不是 `Unlicense`。它只适用于 TelyinCore 主程序和
明确采用本许可的官方内置插件（当前随包提供 `core-infinity-qq`），不覆盖第三方插件、模型、依赖或运行时。历史移除组件的许可不因移除而改变。

未来授权变更时，应同步更新清单中的 `license`、实际许可文本和本规范，不能只改显示字段。
上方模板里的 `license: "MIT"` 只是第三方插件可以选择的一种示例，不会自动为内置插件或
任何未明确授权的项目授予 MIT 许可。独立原创的附属插件可以选择自己的许可；修改别人的插件
先取得原许可授权并注明原作者与具体改动。

附属插件应使用公开扩展接口，不得通过覆盖、补丁或运行时替换官方实现的方式规避禁止直接修改的约定；文档明确允许的扩展点除外。
开发者必须对其实际编写的代码享有相应权利；复制、改名或简单包装官方代码，不构成独立原创。
引用第三方代码须遵守其原许可，标注来源不能代替授权。不得冒充官方或声称未经确认的官方背书。

插件可以仅在本地使用，无须上传 GitHub；也可以公开发布或单独商业销售。
公开或商业发布时，应随包提供以下说明（不要求向平台上传用户配置）：

## 3. 生命周期

入口必须提供 create(ctx)，返回实例。start()、stop()、tools() 为可选方法；未实现 stop 只适用于没有待释放资源的实例。
import/create 阶段不启动后台工作、不安装依赖、不发外部请求。连接初始化放在获准的 start 路径，部分初始化失败也要留存已获得资源并收尾。
当前同步宿主停止路径不会等待 `async def stop()` 返回的 coroutine/Future；返回 awaitable 会被判为停止未完成。不要用 `create_task()` 后立即返回来冒充同步 stop 已结束，也不要在已有事件循环中嵌套运行循环来绕过合同。
stop 必须关闭并确认线程、连接、定时器和自己启动的子进程已终止，防止重载后双监听、重复发送。`Timer.cancel()`、发出停止信号或有超时的 join 返回，都不单独证明回调/线程已结束。
宿主对线程属性的检查只是补充，不能覆盖插件隐藏的线程池、回调、进程后代或外部服务。作者仍须逐项承担资源归属和完成证明责任。
不得终止其他 Bot 或用户手动启动且未经归属确认的进程。
保存配置时，已启用插件由宿主重载；停用插件只保存，不自动启用。
重载可能断线，也可能因旧实例未排空而拒绝，不是无损热替换。关闭失败必须保留旧实例、通道和运行根的责任；不得清掉引用后让新实例抢占。
配置重载失败可能尝试还原配置或恢复原实例；这不是原子事务，也不能撤销已发出的外部动作。分别报告保存、关闭、回滚及恢复的结果，保留最初异常和附加清理失败，不自动重试产生副作用的动作。
详细停止顺序及共享身份规则见第 14 节；候选内部 helper 不是第三方可直接调用的公开扩展 API。

## 4. 宿主上下文

基础字段：name、packageDir、root、botDir、dataDir；后三者在基础装配中指运行数据根，
不能把 botDir 直接当作 persona 所在 Bot 文件夹。宿主可扩充字段，不得依赖 QQ 专用字段作为通用 API。
可选能力包括 log、push_event、read_events、latest_cursor、model_facts；使用前检查 callable。
不要假设任意部署都提供所有能力，未提供时应明确不可用，而不是伪造成功。

```python
def create(ctx):
    from telyincore.tools import ToolDef, ToolTag

    def read_status(**kwargs):
        return "演示插件可用"

    class Demo:
        def start(self):
            log = ctx.get("log")
            if callable(log):
                log("演示插件已启动")

        def stop(self):
            pass  # 真实插件在此释放资源

        def tools(self):
            return [ToolDef(
                name="demo_read_status", description="读取演示插件状态",
                parameters={"type": "object", "properties": {}},
                tags=(ToolTag.READ,), handler=read_status)]
    return Demo()
```

可复制 templates/plugin 骨架；模板不作为内置插件自动安装，不包含用户数据。

## 5. 事件、工具与重复执行

外部输入通过 ctx 的 push_event 报告，不直接绕过主循环请求模型。
事件声明 type、source、text、origin；ts 可由宿主补充。平台消息建议提供稳定 senderKey、
conversation、message_id、自身账号标识和 dedupKey，防止回连补读与实时事件重复入站。
以当前宿主 EventStore 字段验证为准，不能把建议字段当作任意可执行指令。
工具返回 ToolDef，必须有独立前缀、description、显式 parameters 和 handler。
READ/ACT/SPEECH 等标签以 telyincore.tools.ToolTag 实际枚举为准，不用标签规避副作用约束。
发送回执应区分“请求提交”“协议接受”“对方收到”；异常不得伪装成成功。
消息重投和服务重连须有稳定身份与去重策略；幂等键不是自动重试授权。工具可能已经执行而回执尚未提交，未知结果必须保留为 pending/incomplete，不补执行、不自动重派、不重复扣费或 ack。
批次中一项失败不抹掉已定案的成功前缀；保存每条定案回执后再 ack。取消应原样传播，不包装成可重试网络错误。具体批次查询和账本责任见第 15 节。

## 6. 消息标记与平台词表

经历页要说明每一条“哪一路来的”。正文开头的平台标记由插件写入，识别规则与显示词也由插件声明；
核心不认识任何平台名。声明放在清单的 telyincore.channels。

```json
{
  "telyincore": {
    "kind": "infinity",
    "api": 1,
    "channels": [
      {
        "label": "Q",
        "markers": [
          {"scope": "群", "filter": "answered",
           "pattern": "\\[QQ群(?<room>-?\\d+)·消息#(?<id>-?\\d+)\\]\\s*(?<who>[^：]+)："},
          {"scope": "私",
           "pattern": "\\[QQ私聊(?::(?<room>\\d+))?·消息#(?<id>-?\\d+)\\]\\s*(?<who>[^：]+)："}
        ],
        "speech": {"tools": ["qq_send_text", "qq_send_reply", "qq_send_voice"], "text": "text",
                   "destination": "{scope}:qq:{target}"},
        "routes": [
          {"scope": "私", "pattern": "^(?:private:)?qq:(?<room>\\d+)$"},
          {"scope": "群", "pattern": "^group:qq:(?<room>\\d+)$"}
        ]
      }
    ]
  }
}
```

label 为平台显示简称，scope 为会话类型（群、私、直等）；同一平台可有多个 markers。
markers.pattern 必须从正文开头匹配；命名组 who 提供发送者，room 可选，有 room 才允许点开。
pattern 使用浏览器写法（(?<name>…)）；服务端使用的规则还须兼容命名组转换后的 Python 正则。
示例：正文 `[QQ群123456789·消息#123] 某某：早` 显示为 `[Q·群]某某说：早`，
点开后为 `[Q·群·123456789]某某说：早`。私聊相应显示 `[Q·私]`，点开为 `[Q·私·对方账号]`。
正文标记本身不改写。整个前缀同色、无下划线；可点击部分支持键盘操作，并公开 aria-expanded 状态。
私聊的 room 应由插件写入标记；旧标记没有账号时，仅可用该条记录确切的 scope 补全。
两者都缺账号时不显示链接，不做推断。

filter 只认 answered。声明后该类来话仅在她参与对话时进入经历：她发言的工具调用以
trigger_message_id 指明接住的来话；某一轮她发言但未带锚点，则该轮来话全部计入。
未声明 filter 的来话保持全收。speech 声明哪些工具算她发言、正文位于哪个字段；
仅存在于工具调用、没有对应 assistant 消息的发言（如主动私聊）据此补入经历轴。

routes 将记录中可信的会话标识映射为前缀，room 用于点开会话号；不从上一条消息或昵称猜来源。
来话按标记和可信 scope 显示来源；assistant 发言按记录的 scope 或可验证的工具发送目标显示来源。
宿主终端来源由核心提供，外部平台的显示简称、标记和目标格式均由各自插件声明。

speech.destination 是可选的发送目标模板，仅替换 `{参数名}`；参数名以英文字母或下划线开头，
值只能是字符串或整数，不接受布尔值、浮点数、数组或对象。模板最长 512 字符。
例如上例将 scope=group、target=123 替换为 group:qq:123。
结果必须完整匹配该通道的 routes 才接受。发送目标与请求来源不同时，以明确的发送目标为准；
声明了模板却缺字段或结果无效时，不冒用请求来源。未声明模板的旧插件仍可使用记录已保存的 scope。

新经历投影透传可选 scope；旧投影仅按角色、原文、原始时间戳精确回连，不丢掉毫秒，也不按相近时间猜测。
既无可信 scope、也无可验证发送目标的旧记录，会如实显示“来源未记录”。
整理账本显示为“记下”，不冒充外部发言；工具独有发言只补入主对话，不重复加入每份账本。
来源标记不是发送成功或对方已读的证明，实际投递状态仍以对应工具回执为准。

以上仅影响经历页显示，正文转录与模型可见内容不变。
新增平台（微信、B 站等）由该平台插件增加 channels，核心与前端无需改动。

## 7. 通用配置页

config.example.json 定义默认字段，宿主可生成通用表单，无需修改 app.js。
轻量 schema 支持 properties、type、title、description、default、enum、minimum、maximum、
readOnly、writeOnly、format=password。不是完整 JSON Schema，不依赖 required 等未实现关键字。
密钥不回显；通用表单中的留空保留原值，清除需显式操作。其他专用 API 不得自行沿用这套空值含义。
revision 只有在权威写入边界完成比较后才防止旧页面覆盖新配置，前端检查或写入前单独读取不能替代原子比较。
保存前备份原字节至插件 .config-backups；不要将备份纳入分发。
当前通用配置机制以已安装插件目录为范围，不保证所有第三方插件天然拥有每 Bot 独立配置。

### 7.1 统一导航、图标与原生页面接入

侧边栏和页面路由统一使用 src/web/client/plugin-ui-registry.ts。
未注册原生适配器的插件自动使用本节通用配置页，状态直接取 enabled / loaded；
无需在 main.ts 或 infinity-plugin-page.ts 添加包名分支。

清单可添加 `telyincore.icon`，值为 shell.ts 的 ICONS 键名，例如 chat、eye、book、
contacts、chip、history、grid、store、puzzle。未知键回退适配器图标或 puzzle；
不接受 SVG 字符串、URL 或任意 HTML。所有图标保持 20×20 画布和同一线宽。

需要宿主原生交互的内置插件只在注册表中注册一次：

```typescript
registerPluginUI('core-infinity-demo', {
  icon: 'book',
  createPage: demoPage, // (shell, name) => {root, show(), stop()}
  health: { // 可选；只读状态，不在轮询中启动进程或下载
    endpoint: '/infinity/demo',
    signals: (snapshot, plugin) => [{state: 'on', label: '服务就绪'}],
  },
});
```

show 启动页面观察，stop 停止定时器并释放临时资源。原生适配器仍需随宿主构建，
不代表第三方 Python 插件可动态执行宿主 JavaScript；第三方定制页使用第 8 节隔离桥接。
状态统一为 on / off / warn 和可读 label；失败时退回真实生命周期状态，不保留旧的就绪快照。
展开侧栏保留多状态点；折叠侧栏显示一个角标（warn 优先），详情在可访问名称与悬停提示中。
不要让插件自行拼接侧栏 DOM 或依赖固定侧栏宽度。

原生模型设置页以 QQ 连接「语音模型」为唯一排版基准，不新增插件专属表单布局。
共用 src/web/client/infinity-controls.ts 的 infinityField、infinityToggle、
infinityModelPicker、infinityVoiceHeading，分别用于字段、启用开关、模型选择和卡片标题。
沿用 infinity-voice-grid → infinity-pane → infinity-voice-card 结构；

## 8. 自定义 HTML 桥接

configPage 为插件内部不超过 256KB 的单文件 HTML；脚本和样式自行内联。
iframe 仅 allow-scripts，无同源权限；默认不允许外部网络、表单导航或读取框架页面。
旧插件自建 WebUI 不会自动兼容，需按以下消息契约适配。

```javascript
parent.postMessage({type: 'telyincore:config:get'}, '*');
// 收到 type=telyincore:config:state 后，从 message.config 取得 fields 与 revision。
// fields 中 path 为字符串数组，私密字段 value 不回显。
parent.postMessage({
  type: 'telyincore:config:save', revision,
  changes: [{path: ['greeting'], value: '你好'}]
}, '*');
// 收到 telyincore:config:saved，检查 ok；成功后重新 get 获取新 revision。
```

页面接收消息必须检查 event.source === parent；宿主只接受当前 iframe 的消息。
不要在 HTML、日志或描述里硬编码密钥。详细契约见 docs/design/24-第三方插件配置页.md。

## 9. Bot、通道与进程隔离

运行中 Bot 固定，切换通过重新启动选择完成；多 Bot 可多开端口。
不得把平台昵称等同于跨平台身份；账号归并须通过核心已确认身份关系处理。

共享外部服务应校验账号、端口及进程归属，不因 TelyinCore 启动而静默启动软件、扫码或接受条款。

## 前端页面异步加载约定（并参见第 16 节）

Core 页面、内置插件原生页及通用配置宿主统一遵守：

## 14. 异步工作、停止与最终释放

本节是插件作者与宿主集成方共同遵守的责任合同。`PluginIngress`、`IngressShutdown`、custody 和 completion 属于核心接线概念；第三方不得复制内部 token、调用私有释放 helper 或 monkey-patch 宿主来取得权限。

### 14.1 在开始工作前登记所有者

- 每个已接受动作必须关联原插件实例、所属 Bot/root、通道和本轮生命周期。先登记责任，再调度；禁止存在“工作已启动但无人持有”的窗口。
- 返回 cold awaitable 时，区分“对象已创建”“已获准执行”“真正完成”。未 await 不等于没有登记责任；不得因调用方丢引用而解锁或复用。
- 线程、Timer、async task、Future、队列项、模型请求、子进程及其读写线程都要纳入观察范围。后台整理链的前驱和独立 close 任务同样是工作，不能只看最新尾任务。
- `shield` 只隔离取消传播；被保护的任务仍可能运行。取消观察者、超时退出等待、空任务列表、GC 或日志中出现“关闭”都不是完成证明。
- 串行链必须等待提交时仍未完成的前驱；尾节点被取消不能让后来任务越过仍在执行的前驱。

### 14.2 停止顺序和失败责任

- 先不可逆关闭原实例的新准入，再观察已接受工作；停止信号不得顺带清队列、丢回执或重新派发。
- 固定原 owner 与既有截止时间，等待属于它的任务、前驱、close 和回执责任。不得换新实例查询空状态来代替旧实例排空，不得每次等待重置超时预算。
- 停止后的 held lease 应同步撤销；之后的消费必须检查原 lease 仍活动、仍属当前生命周期。仅检查一个全局 stopped 标志不足以阻止旧代任务继续使用资源。
- 超时表示本次等待预算耗尽。真实工作未终态时保留 owner、实例、channel/root 和失败责任；不能为了让关停成功而移除 registry、清队列或丢锁引用。
- 在实际释放之前检查所有公共与私有屏障；释放回调返回后、发布完成回执之前再次核验身份。成功释放与完成身份发布之间不能留下把原 owner 误认成 foreign 的窗口。
- 共享 `scope.finish` 之前固定 custody、handle、scope、ingress 的原对象基线，包括没有 handle 的分支；内层不得重新捕获等值替代对象。先登记 finish 已尝试；异常或取消后不得由 fallback 重复 finish/release。
- 最终完成回执只能绑定原生命周期，不能重新开放准入或授权再次释放。失败路径保留原责任；成功路径可用身份回执继续验证退役对象，但不得伪造回执或靠对象数值 ID 相等替代同对象验证。
- 保留最初主异常与取消因果链，另附清理失败；异常格式化本身失败也不能覆盖主异常。清理失败不能因后续某一步成功就清零。

这些合同已有组合回归及部分真实生命周期验收支持；覆盖范围按模块和运行路径分别报告。局部替身或一次正常退出不能证明所有 GC、取消、强杀及设备错误时序。

### 14.3 PluginIngress 的同实例观察接口（按宿主版本核对）

本次 E/I 集成版本提供以下核心接口，使用前须确认部署确有同版本 producer 与 consumer；它们不是所有 API 1 部署天然具备的 ctx 字段。

- `begin_shutdown()`：同实例不可逆、幂等关闭新准入，不取消已接受工作、不清队列。
- `shutdown_state()`：返回只读快照，字段包括 `accepting/pending/buffered/failed/drained`；其中 failed 为持续留存的失败计数。不得把 `drained=true` 当成失败已解除。
- `shutdown_tasks()`：返回当前运行 loop 上的 shield Future 观察器快照。它不是 coroutine factory，不要 `create_task(observer)`；取消观察者不取消或重放原工作。
- 等待结束后重读原实例状态。观察器为空不证明 buffered/failed 为零；跨线程调用者的 30 秒等待超时也不证明已接受 action 停止。该数值是 producer 当前边界，不是所有插件的统一预算。
- 本次 I 集成公共/私有释放屏障还检查 `receipt_pending` 与 `release_failed`。只有关闭准入、pending/buffered/failed 均为零、drained 明确为 true、回执无 pending 且释放无失败，才满足这一道屏障；其他资源屏障仍须分别满足。
- 共享观察返回类型必须按合同校验。例如回执 producer 的 `pending/incomplete` 必须是精确 bool；`None`、`0`、空容器或缺字段不能被宽松真假判断当作“没有责任”。

等待失败、循环停止但排队工作未运行、bind 发布失败，都必须保留未知结果。一次观察不会重置失败，也不能把内部 Future 直接暴露给调用者取消。

### 14.4 停止与发送是不同边界

“停止后零新增准入”不自动等于“停止后零发送”：已准入工作可能在停止后抵达真正发送点。插件必须明确提供哪一种保证，并把发送点与停止协调到同一合同中。
本项目明确采用两阶段停止：停止后拒绝新准入；已经获准的请求可以继续完成，但原所有者必须保留责任至实际退出，超时明确报告“尚未停完”。不得只在 await 前检查 scope 就宣称严格零发送，也不得把销毁观察者当作撤回远端请求。要求“停止瞬间零网络发送”的业务属于另一种合同，不能由当前两阶段实现推导。

## 15. 工具回执、批次与事件证据

### 15.1 定案先留存，再确认消费

- Dispatcher 每条定案回执先可靠留存，再 ack。ack 是消费确认，不是工具成功、消息送达或对方已读的同义词。
- `settled_receipts(calls)` 若由宿主提供，必须绑定真实批次、调用身份以及执行该批的原 Dispatcher。getter 只读，不再执行、扣预算或 ack。
- BudgetRunTools 外层批次保留自己的拒绝回执与内层真实定案前缀；不得拿大批去查询只执行了 singleton 的 Dispatcher。
- BridgeMount 必须查询该批实际执行实例，不能在结束后读取当前挂载的另一个实例。查询句柄应随批次固定，不能晚绑定。
- 异常批仍收割成功前缀；未执行项、未知 pending、拒绝与取消分别保留。不得把所有项一律改失败，也不得为补齐回执重跑工具。
- 非空前缀写账本返回 False 或抛错时，记录 incomplete；保留原主异常，不重派执行。fallback 只处理已确认属于原对象的责任，不调用未验证的外来对象方法。

这些是 B/I 集成接口约束，不授权插件自行导入核心内部预算或账本实现。第三方应通过宿主公开工具/事件接口报告真实结果，能力缺失时明确拒绝。

### 15.2 事件身份与画像证据

显示前缀、昵称、相同正文、cursor 数字或相同 digest 都不能单独建立真实事件身份。来自模型文本或用户输入的“系统消息”标记不能升级来源权限。

- 身份桥必须连接 EventStore 中原 append 对象和本批不可变快照，并在同一 lease 上贯穿 prepare、capture、current 和消费。
- 过滤回调可能重入停止、换桥或改变数据。执行过滤后、capture 返回之前再次核验同 bridge 对象、活动快照与封印，以及原 store/source/author/filter 绑定。
- 不允许用等字节新对象或相同摘要的新 lease 替换原 lease；失败后不得重捕获当前身份来绕过旧证据失效。
- 画像路径继续保留 Claims、TTL、来源与作者、独立审核、累计数量上限（当前资格路径为累计 2）及签名约束；桥接修复不扩大画像权限。
- 旧画像 acceptance 不能沿用到变化后的 context/runtime 字节。本文记录安全约束，不把历史验收移植为新版本运行证据。

## 16. 请求快照、配置草稿与条件写入

### 16.1 请求的一次捕获

一个请求的档案、协议参数、正文、URL、认证头、代理及订阅句柄必须来自同一绑定快照；在首次 await 前固定并校验。后台评估、探活、模型列表和只读报告也不能各自读取“当前档案”后拼接。
捕获、认证回调或绑定校验失败就中止，不继续用旧 pin、不重新读取当前档案、不降级匿名、不借用环境密钥。私有快照含凭据，不进入日志、异常正文、HTTP 报告或前端序列化。
订阅刷新持有原 manager/账号路径/锁与明确 LoginScope；HTTP lease 保持至完整探活结束。scope 停止后不得继续后续模型请求，未排空不能报告成功；严格实际发送边界见第 14.4 节。

Chat 流没有 DONE/finish_reason 就遇到 EOF 时，不制造 completed，也不定案残缺工具调用。打开流之后的协作取消单独传播，不能进入网络重试或补执行分支。

### 16.2 页面动作冻结与两阶段保存

- 点击时冻结档案身份、目标和密钥草稿，后续 await 不读取用户已切换到的新档案或新输入。页面代次只防止晚响应绘制，不能代替后端写入校验。
- 配置保存使用本次响应中的权威 `profile` 与 `secret_binding={profile_name,secret,revision}`。后续密钥写入原样传 expected，只写该回执的 secret 槽。
- 不从刷新 report 推导 binding，不由服务端补当前 expectation，不在冲突后自动重试。后续配置保存会使旧 binding 失效；缺失、过期或槽归属变化必须拒绝，冲突映射为 HTTP 409 的消费合同需对应部署实现。
- 本次 A 集成在同一跨进程文件锁内重读配置、核对 binding 并替换密钥；只有遵守同一锁协议的进程才受此保证。配置与密钥仍是两阶段操作，不是双文件事务。
- 配置已提交而密钥写入失败时，如实报告部分保存，保留可恢复草稿；不能显示整体成功，也不能擅自回滚或重复外部动作。单行密钥校验不能被错误回显绕过。
- 已存档案的目标改变时，探活和模型列表应先要求保存，或明确创建独立草稿；新输入密钥不能绕过已存档案目标绑定。独立草稿不得借用其他档案的密钥槽。

上述 binding 是 A/D 条件密钥写入合同，不等于第 7 节通用插件配置页 API 自动新增相同字段。对接时以准确端点合同为准。

### 16.3 公开状态与安全命令

`web_report_snapshot()` 从同一次捕获生成公开报告；`availability[profile_name]` 只表示该档案 model 去空白后非空，不表示网络、认证或协议能力正常。`can_probe` 也不是探活成功证明。
探活响应、错误与命令日志要脱敏，不能将上游反射回来的 key/header 原样发送到页面。测试应检查响应和日志，而不只检查正常结果。
`/say` 等入口须执行可信 Host/Origin 门禁，不能把 loopback 或浏览器页面存在当作任意调用授权。Waves 等可配命令前缀下的群凭证拒绝要同时覆盖桥接和服务端；改前缀不能绕过策略，失败回执不能伪装成功。普通日志不得记录凭证命令正文。

## 17. 身份确认、数据完整性与分区

### 17.1 身份变更

解除绑定须把同一次权威快照中的 person 与 revision 呈现给操作者，保留原确认值直至提交；不能在执行时查询当前值再悄悄补齐。
权威写入点在同一写锁内核对 `expected_person_id`、`revision` 和确认条件。过期、归属变化或未确认都拒绝，不自动刷新确认或重试。
本次 C/F CLI 的 list 输出为 `{people: [...], revision: string}`，不再是裸数组；unbind 需要显式 `--expected-person-id`、`--revision`、`--confirm`。外部消费者必须逐个核对兼容性，不能以合成消费者代替真实调用方验收。
单实例 RLock 不构成跨实例或跨进程锁。插件不能把同一进程内测试通过写成多进程事务保证。

### 17.2 知识、索引与向量维护

- 同步前完整读取所需知识与有效做法；区分权威空全集和读取失败、部分读取。只有显式 `authoritative=True` 的完整空全集才允许清理目标分区旧索引。
- 索引同步真正成功才清 `.needs-sync`；读失败、提交失败或结果未知保留标记和责任。枚举至 commit 的并发窗口仍须单列，不能宣称跨进程全集事务。
- 关系裁剪按每个 source 保留最新 favor/blocked 原始状态，不能只保留聚合结果而丢失原来源语义。
- 使用当前 Bot 的明确运行数据根，不把共享目录、其他 Bot 的缓存或身份资料混用。迁移、知识修改或重建索引后另核对向量覆盖；缺向量不等于丢原文。
- 检索向量缓存、主模型 KV 缓存、提供商 Prompt Caching 分别报告。不得靠提高请求内补算阈值、隐藏 WARN、删除旧向量本或跨 Bot 复制来“修绿”。
- 向量维护仅补当前内容指纹缺项，核对模型、维度与归一化，保护原有数据和并发变化。计算、模型下载、真实召回验证须另获范围；未经验证不得宣称语义检索完全恢复。

## 18. 安装、发布与恢复边界

### 18.1 安装的每个路径都要校验

本地目录、远端归档、真实 HTTP 入口和异常分支必须使用同一最终名称/路径规则。不能只在 UI 或一次预检查中验证，随后信任 manifest 改写出的目标。
解包限制、普通文件检查与路径限制要在写入前完成；拒绝越界、链接和特殊文件，最终目标仍在允许根内。不能只靠字符串 startswith 判断祖先关系。
仅凭名称安装没有可信 resolver 时明确失败，不猜 URL、不偷偷访问注册表。下载成功、解包成功、安装成功、启用成功分开报告；异常返回也必须有确定的错误与责任状态。
安装不得覆盖别人的目录或私密配置。备份、暂存和失败残留的清理必须限定原所有者与范围，不能递归删除目标目录来绕过冲突。

### 18.2 默认不可变版本发布与自定义路径发布

默认 Web 发布使用不可变 generation 与指针切换，消费者固定读取对应版本；旧版本保留，不能在仍有消费者时擅自清理。默认构建与实际页面资源已完成本次部署核对。自定义/legacy 输出仍使用两次 rename，只适用于无并发写者、无活跃消费者的受控场景：先暂存，再把旧输出移到备份，最后将暂存移到目标。
两个 rename 中间可能没有目标目录；路径检查与使用之间仍可能发生换链。因此不得宣称完整原子切换或抵御并发路径替换。
首次备份移动失败（包括 ENOENT）不能被当成“原目标不存在”后继续发布。发布失败且回退也失败时保留两份错误和首次 cause，以及 phase/output/stage/backup；不自动删除备份和失败暂存。
自定义输出的跨目录、跨卷、并发消费者或严格原子需求必须另行设计和验收，不能通过文档升级这个保证。

## 19. 回归、证据留存与交付

### 19.1 先冻结输入，再决定是否执行

- 登记主源码、supporting 源码、动态加载对象、AST 选取符号及传递依赖的真实路径、大小、SHA256 和归属；supporting 不自动取得修改权，也不自动成为完整导入闭包。
- 新补丁核对 before 哈希，漂移即停；按最小 hunks 集成到新离线副本，不整文件覆盖他线工作。旧验收、旧 loader 摘要不能套用新字节。
- 历史与组合测试模式显式分开；固定清单自身摘要，再核对来源文件大小和摘要。不得使用“任意已有路径”fallback、双哈希宽松放行或删断言迁就变更。
- 测试收集、AST 编译、模块加载也可能执行代码。未获准时只交源码、静态意见和哈希，结果写 NOT_RUN；人工用例数不是收集数。
- 准入须覆盖解释器、pytest 自动插件、conftest、动态 import、原生依赖、临时根、回环监听、线程、async task、Node/esbuild 子进程及完整后代清理。缺 `.pyc` 不是缺包证据，存在安装元数据也不是导入成功证明。
- 引用源码需要许可与原批准依据；路径与 SHA256 只能证明字节身份，不能证明使用授权。本轮两份历史语音 reference 已获准仅作隔离合成测试输入，不构成部署旧 TTS 产品的许可；新的引用仍须逐项核对，不用弱模拟或 skip 求绿。

### 19.2 必须覆盖的合成场景

- 准备中途异常与取消、线程/Timer 仍活、跨线程等待超时而原工作稍后完成、shield 前驱仍执行、close 独立任务失败。
- 原 owner 被等值替换、无 handle 共享 finish、释放回调内换身份、释放成功后完成回执发布失败、fallback 不重复收尾。
- 批次成功前缀加拒绝/取消/失败、外来批次查询、getter 零重派零重复扣费、账本返回 False。
- 回调内撤销身份桥、同 digest 新 lease、prepare/消费间换桥；保留原隐私、范围和画像强断言。
- A/B 档案切换屏障、认证捕获失败、无终态 EOF、两阶段部分保存、晚 HTTP 回调、旧身份确认、Case/case 保存碰撞和路径越界。
- 清理自身失败仍尝试后续有明确归属的清理步骤，末尾汇总；fixture 创建一半即失败也有所有者。清理日志不能替代实际退出、join 和资源状态证据。

这些场景是回归要求，不表示本稿执行过这些用例。涉及真实账号、真实业务数据或网络的验收须另行授权并单独报告。

### 19.3 报告持久保存与不完整终态

pytest call 报告通过不能替代 teardown；超时、取消、缺失 teardown、清理失败或日志截断必须保留各自维度，不能折叠成一个 PASS。`user_properties` 里的 attempted 只表示尝试，不证明报告持久保存。

I r17—r22 的证据设计区分运行资源 `G_run`、证据资源 `G_evidence` 与外部观察者 `G_observer`。C 是运行收尾截止，L 是唯一迟到附证窗口的实际结束，D 是证据收尾截止；它们来自明确同源的监督时钟，不能拿 worker 时间驱动监督 deadline。
主清单 M 发布时只记录已知 C 与 late 计划，不预填未来实际 L。唯一迟到附证关联原 M 并记录实际 L；L 后事件不再扩展覆盖，不重写主清单或追加无限附证。观察者不能自证自己已经退休。
ACK 的确认范围要明确对应清单摘要、精确段字节、长度及 frame/producer/receiver 前缀，不能把部分持久保存说成整个运行成功。截断诊断不会因为有 ACK 就变完整。
序列化、排队、写入和提交确认都受明确容量/时间边界约束；背压或证据截止失败必须保留不完整状态，不无限阻塞清理，也不以丢报告换成功。

**当前证据状态：I r41 已将既定 1157 项测试及 57 项子测试接入实时监督，8192 条源事件持久化，完整诊断和主/迟到附证单独封存；这是测试执行监督，不是所有生产请求的常驻监督器。** 本地 ACK 只证明对应字节已 fsync/readback，不证明业务成功或远端收到。用户仅保留本地报告，外部 ACK 不在本次适用范围。 模拟 ACK、retired 标签及显式耗时不是磁盘 flush/readback、真实身份或进程排空证据；模型的 `simulation_only=True / NOT_ATTESTED` 不得转为真实验收结果。180 秒执行/15 秒清理等历史提案不是本手册授予的默认批准参数。

### 19.4 分开报告四种结果

- 文档/源码交付：列出修改范围、完整 before/after 摘要、最小补丁及剩余合同缺口。
- 静态复审：仅说明审了哪些字节与条件；补丁可应用不等于语法、导入或测试通过。
- 有限合成回归：只有获得准入并实际执行后才能填写真实命令、退出状态、报告位置、超时和清理结果；缺失证据如实标记。
- 主仓落地与真实运行验收：分别授权、分别报告；不以离线候选、静态接受或合成回归通过宣称已部署或真实服务恢复。

交付证据不得包含密钥、账号令牌、用户消息、人格或知识正文。历史日志和历史 acceptance 保留其原日期与适用版本，不能用新文档“更新”为当前通过。

## 20. 崩溃、人工恢复与诊断未知

正常退出、协作取消、进程骤停和系统断电是不同路径。原 HOST 正常退役要求原对象/句柄、完整排空及原登记身份核对；PID 消失、drained 标签或磁盘 JSON 都不能重建原 HOST 权限。

### 20.1 停止后仍保留责任

业务已执行但回执未持久化时保持 unknown/incomplete，不自动补执行、补扣费、补 ACK 或重复外发。只读预览无法获取有效上下文时可明确返回 unknown；真实请求不得因此匿名降级、借用旧绑定或制造 completed。

### 20.2 受控维护工具不是插件 API

r49 独立维护入口提供 prepare、execute、status、renew。它限于固定 Telyin 部署，不向插件公开，不允许插件调用它绕过宿主责任。恢复计划固定 Bot、账号/存储/版本、来源字节及 inode、保护配置、代码集合摘要和有效期；存在活跃服务或未对账 HTTP/login/mutation 时拒绝执行。

人工明确接受旧业务结果 unknown，只允许继续指定的归档事务，不等于认定旧业务成功或外部账号离线。过期计划须重新核验并形成新摘要，不能按当前原件重捕获期望；报告丢失只能核对持久证据，不能重放业务。

### 20.3 保留证据与原件

历史归档使用独立 UUID 目录及短文件名，避免在退出最后一步扩长路径；保持原字节及 inode，禁止覆盖已有目标。备份、失败暂存、未知记录按所有者单独处理，不递归清空。计划或归档文件残缺、身份变化、来源和目标双存等情况继续阻断。

工具通过合成跨进程骤停测试不等于任意断电恢复保证。不得为了“测试恢复”擅自强杀用户运行中的 Bot、QQ、TTS 或模型服务。

## 28. 异步责任、持久化及请求隔离补充（r82 引入）

### 28.1 拒绝调用不等于工作不存在

同步钩子返回已启动的 Future 时，禁止将其当作权限通过，也禁止任意取消或调用不明对象的 `close`。原 Dispatcher 必须保留工作及完成异常，外层预算、事件账本、分享桥和释放判据要查询同一执行者。更换当前 Dispatcher 不得丢弃旧执行者的责任。

观察应分开表达“仍在执行”和“执行已经失败”。任务结束可以清除待完成状态，但不能清除失败记录。状态接口必须保持既有类型合同；外层需要映射或计数时，不能用布尔值替代集合，造成收尾报告再次异常。

### 28.2 线程取消与操作预算

`asyncio.to_thread` 的等待被取消，不代表线程退出。线程仍可能读写文件或发出请求；必须保留归属并观察真实终态。不能把取消后的工作留给无人观察的执行器，也不能在同一责任未结束时重试业务。

操作预算与收尾期限是不同维度。Strata刷新保留三秒操作预算；超时或取消后，拥有者仍等待原线程退出，期间不能发布迟到能力快照。外层停止期限耗尽时应报告未完成并保留责任，不得以延长预算、强杀线程或忽略错误取得通过。线程最终失败与原取消同时存在时，两者的因果都须留存。

### 28.3 持久化与并发写者

记忆正文、知识和经历文件应先写完整暂存文件，flush/fsync后发布；已存在文件发布失败时保留原字节，新文件使用不覆盖已有目标的创建语义。合作写者使用同一来源锁；来源变化时拒绝提交。此合同不包含恶意路径替换、任意外部编辑者或硬件断电保证。

事件库保留独立游标高水位，清理分片前先持久化高水位。高水位损坏时先拒绝，不能先修日志尾部再报错；不确定追加后应封住当前实例，重开核对，禁止自动重放。只读事件观察不创建目录、不修尾、不清理。跨进程测试必须证明竞争写者不会重复游标或覆盖别人的提交，不能只测同线程对象。

同一规范化闹钟表在一个进程内只允许一个活跃调度驱动，驱动取消及等待子任务清理结束后才能交还所有权。这不是跨机器分布式调度保证。

WakeBus停止时应先封住新事件，再撤销原定时句柄。已经排入循环的迟到回调不得恢复唤醒；撤销失败必须保留句柄和错误。未消费事件保留在状态中，不能以“没有定时器”宣称全部工作完成。

安装器也属于后台任务。创建线程前将其登记给同一个根拥有者，停止后拒绝新安装；已经接受的安装可以继续，但根关闭必须观察该线程实际退出。线程启动失败和运行失败都不能清空成成功。不能使用daemon线程退出代替安装收尾，也不能代替用户自动删除失败暂存产物。

### 28.4 请求快照与展示隐私

一个启动动作的配置解析与下游组件必须来自同一次字节捕获，不能由下游重新读取同一路径。知识页只读知识所需来源，不能因无关私有材料读取失败而阻断公开的知识响应。

同一批次的身份提示、画像目标和检索权限共用一个不可变身份修订。绑定变化时拒绝继续使用旧视图，不在请求中自动刷新到另一身份；新批次重新捕获。只读视图不提供写入授权，解绑和合并仍在权威提交点比较期望修订。

Waves矩阵角色记录按命令触发器建立独立作用域，并在成功、异常或取消时撤销。继承的迟到上下文不能继续补写角色身份；没有有效作用域时宁可不加交互身份。遮罩后的UID不得继续藏在HTML命令属性中。

头像保存可以取消等待；迟到回调不能重开已关闭的对话框。取消浏览器请求不等于服务器回滚。两阶段QQ设置首步已提交、后续动作失败时，应报告部分成功并保留用户草稿，不得自动把旧设置写回覆盖并发修改。

### 28.5 每次执行证据单独封存

每次组合运行保存独立源码摘要、执行参数、XML结果和实际导入来源，运行后核对源码未变化。后来的定向测试不能覆盖前一次组合证明；增加修复后应按影响范围验证，最终再组合。

AST抽取的方法测试、查询替身、合成DOM、TypeScript转译和真实依赖运行是不同证据。查询替身通过不能声明SQLAlchemy方言验收；转译通过不能声明完整类型检查；合成页面通过不能声明真实浏览器布局验收。缺少依赖或环境时明确列出，不将缺项写成通过。

探针退出码必须反映报告判据。超时、失败、空测量和需要人工判断不能返回成功。自建传输和报告文件在异常路径也要收尾；借用传输由调用者负责。原异常、收尾异常和未释放对象须共同保留，不能用`gather(return_exceptions=True)`后不检查结果来吞掉收尾失败。

布局验收应在独立浏览器配置中使用合成内容、阻断真实请求，并记录实际视口和DOM尺寸。终端正文与输入框需共享内容宽度、响应式边距及浏览器实际滚动条槽宽；不要硬编码15px来假定所有平台一致。滚动拥有者、父节点和源码注释必须与当前DOM对应。


## 29. 关闭与投递合同补充（r84 引入）

逻辑停止只禁止新准入，不能替代物理句柄关闭确认。同步关闭接口本轮要求返回 None；失败、取消、不确定返回值必须保留原资源和错误，禁止自动重复关闭来制造成功。模型流关闭与 HTTP 客户端关闭分别归属原持有者，借用客户端不得提前释放。清理异常不能覆盖原主异常，异常对象自定义格式化或赋值行为也不能改变这一规则。

发送工具调用仅代表意图。终端明确显示“拟发送（未确认送达）”，并保留结果回执。经验参与投影只接受同一 tool_ref 的唯一调用/结果，结果必须精确匹配插件声明的 speech.receipt 模板和目标，且包含非零 receipt_id。模板中的其他字段只能来自原调用参数；旧无配对身份、排队、拒绝、取消和外来回执不推断成功。QQ 模板确认的是协议端已接受，不证明对方已读。每个新调用均分配宿主生成的持久身份，不能使用工具名称或正文猜测关联。

Ingress 必须在动作及其观察上下文退出完成后发布终态；上下文退出或记录失败应进入同一失败责任。drained=true 仅表示接受动作已终止，不代表可释放，仍须共同检查 failed、pending、buffered 和外层释放责任。取消观察 Future 不得取消或重放被观察工作。


## 30. 未确定投递的查看与人工处置（v1.13）

插件事件的持久阶段账本随Bot目录保存在 `bots/<Bot>/memory/ingress-delivery/pending.json`。绑定的是正式事件库路径；旧data根的登记所有者仍使用旧根，其他Bot使用自己的分区，不能通过固定拼接猜测归属。

- APPENDING：追加是否落盘尚未确定；不能自动当作未发生。
- STORED：已持久化、从未开始投递，只允许按精确游标及内容摘要恢复。
- OFFERING：入队结果尚未确定；失败、取消或回执保存失败均不自动重放。
- QUEUED：已经入队但消费者尚未领取；重启按精确游标和摘要恢复，不等于处理完成。
- PROCESSING：消费者已领取，可能已写会话、调用模型或执行工具；异常或重启后隔离，不自动重放。正常处理或明确过滤丢弃后才移除账本条目。
- RESOLVED：操作人针对同次快照完成明确处置，保留原阶段、游标/摘要、证据摘要和操作人标签。不是系统业务ACK。

总线接收、模型完成、工具执行和QQ接收方实收是不同证据；插件不得从其中一个推导其他结果。

本地运维入口：

```powershell
& 'D:/TelyinCore/core/.venv/Scripts/python.exe' -I -B 'D:/TelyinCore/core/tools/ingress_review.py' --core 'D:/TelyinCore/core' --bot Telyin show
```

show只显示阶段元数据及完整账本revision，不返回事件正文、不改变generation，不声明整个文件系统零写入（协调锁侧文件仍可存在）。人工写入必须使用同次show的entry/revision，明确confirm，填写核对证据SHA256和操作人标签；不自动刷新确认。

```powershell
& 'D:/TelyinCore/core/.venv/Scripts/python.exe' -I -B 'D:/TelyinCore/core/tools/ingress_review.py' --core 'D:/TelyinCore/core' --bot Telyin resolve --entry '<32位条目ID>' --expected-revision '<同次revision>' --decision abandon_no_replay --evidence-sha256 '<64位证据摘要>' --operator local-admin --confirm
```

confirmed_handled表示操作人已核实处理；abandon_no_replay表示明确放弃且不重投，接受可能漏处理。两者都不是程序验证了外部业务事实。证据摘要只绑定人工依据，操作人标签不是独立认证。

只能处置APPENDING/OFFERING/PROCESSING。目标Bot必须已协作退役：运行锁忙、实例登记仍在、身份不匹配、读取器版本不受支持均拒绝。入口不停止服务，不得删锁/登记绕过。两个操作人争抢同次快照只能提交一次。遇到失败先重新show核对：提交后回执丢失时可已为RESOLVED，不得盲目重试。

人工决定与原记录一起提交，不删除事件或审计。已处置记录不会在下次启动重投，也不继续计入未确定责任。账本保持128条及64KiB上界，达到任一上限拒绝新写入，不能自动删除已处置审计求绿；另行受控归档不属于此接口。

当前账本为 schema 2，兼容读取 schema 1；旧读取器不认识 QUEUED/PROCESSING，较早版本也不认识 RESOLVED。处置入口固定校验兼容读取器摘要，不允许仅更新工具就写入新状态。产生人工处置后不得直接恢复旧pending.json或回退旧读取器，必须保留兼容读取器及全部审计。不存在真实待处理条目时，不制造业务事件来演示处置。

## 31. 结项与验收口径（v1.13）

限定合同验收、用户接受的能力边界、后续新增需求分别登记。不得把接受边界改称缺陷修复，也不得为清零无限扩展新保证。
代码与合成验证可以证明受测分支；真实只读查看不能证明真实人工处置，进程崩溃不能替代物理断电。禁止为了验证而擅自操作其他Bot、QQ客户端、TTS或真实账号。
